## 1. 同一句 SQL 为什么还取决于硬件（p2–23）

数据最终存在存储介质上，数据库常按页或块搬运，不是每次只读一个格子。RAM 快但易失；磁盘、闪存等非易失，速度、容量、成本不同；磁带更适合顺序归档。

机械盘一次随机访问要定位磁道、等待旋转，再传输。顺序读相邻块可摊薄定位开销，因此“读 100 条分散记录”可能比“顺序扫较多相邻数据”昂贵。吞吐量说每秒搬多少数据，IOPS 说每秒处理多少次 I/O，不能混为同一指标。

SSD 没有机械寻道，但闪存擦除按块、读写按页，重写涉及映射、垃圾回收和磨损均衡，并不是没有随机访问成本。RAID 用多盘并行和冗余改善容量、可用性等；具体级别不同，不能说所有 RAID 都抗故障，也不能把 RAID 当备份。

课件中的容量、接口速率、寿命与 Optane 示例作为历史教学背景，不能当 2026 年购买规格或通用设备常数。理解机制比记具体型号数字重要。

## 2. 表中的行怎样组织（p24–35）

课件讨论定长记录、变长记录以及不同存储组织。定长记录可按位置计算偏移；删除时可以搬移后续行、用最后一行填空，或维护空闲链表。变长字段用偏移和长度定位，NULL 可用位图表示。分槽页让外部定位到槽条目，页内记录移动时更新槽信息，减少指针失效。大对象可通过外部文件、拆分或 PostgreSQL TOAST 等方式处理。可以把堆表理解为不按查询键自动排序的记录集合；行通过页和位置等信息定位。补充比较：行存便于取完整记录，列存适合某些少列分析；这不是本节已经系统讲完的列存实现。具体地址、行移动、版本保留等依引擎，不应把某种物理位置当永久业务 ID。

## 3. 不想每次从头翻，增加目录（p36–56）

B-tree 类索引按有序键组织，并关联记录定位信息，帮助缩小要检查的范围。联合索引按多列有次序地比较，`(surname,born)` 不等于“单独给 surname 和 born 各建一个索引”。

```sql
CREATE INDEX people_surname_born_idx ON people(surname, born);
```

像先按姓、同姓再按出生年排目录。已知姓可以找连续范围，同时给出生年更容易缩小范围；只给出生年通常不能直接定位一个紧凑连续区间。

主键、唯一约束在课程使用的系统中通常有索引支持，但约束表达业务规则，索引是访问结构。不要用“删掉唯一约束能快一点”破坏数据正确性。

目录并非免费：占空间，插入删除要维护，更新索引键也有成本。p69 的测试图说明取舍，不表示“超过五个索引一定错误”。选择需依据实际查询、数据分布和写入负担。

## 4. 为什么有索引还选择全表扫描（p57–75）

查一个罕见姓，索引可能只找少数记录；查包含大半数据的国家，逐条回表可能比顺序扫更费。选择性看具体条件实际留下多少行，不只看列名或不同值数量。国家分布可能极不均匀，相同列上一个值适合索引，另一个值不适合。

课件从查询排队说明性能为何影响并发：单次省下一点工作，反复执行可能显著减轻排队。OLTP 常见少量记录定位，OLAP 常见大批扫描，但不是“OLTP 绝不扫描、OLAP 绝不用索引”。

## 5. 别猜，读执行计划（p76–91）

```sql
EXPLAIN
SELECT m.movieid, m.title
FROM movies m
JOIN credits c ON c.movieid = m.movieid
JOIN people p ON p.peopleid = c.peopleid
WHERE p.surname = 'Bogart';
```

先看访问了哪些表、从哪里筛选、是否用索引、估计多少行、如何连接、有没有聚合排序。树形计划可从子节点往父节点理解，不能把书写的 FROM 顺序当执行顺序。

补充：PostgreSQL EXPLAIN 是估计，EXPLAIN ANALYZE 实际执行并报告实际统计；对修改语句也会真的修改，不能当只读查看。成本数字不是直接毫秒，不同机器和产品计划也不能只比数字大小。

## 6. 为什么给列套函数可能用不好原索引（p92–114）

索引按原始 surname 排序，`UPPER(surname)='MARVIN'` 比较转换后的值，原目录次序未必直接适用。日期也一样，按整列取年月，常不如直接用日期区间表达可搜索范围。

```sql
-- PostgreSQL 示例；born 在课程模型中只是年份，不适用这个时间戳例子
-- 假定另有 events(event_time timestamp)
SELECT * FROM events
WHERE event_time >= TIMESTAMP '2026-06-01 00:00:00'
  AND event_time <  TIMESTAMP '2026-07-01 00:00:00';
```

`LIKE '%abc%'` 没有固定开头，普通 B-tree 通常无法像等值或固定前缀那样定位；但专门文本索引是另一回事。隐式类型转换若落在列上，也可能改变可用路径。

补充校正：课件说联合索引缺首列就“不能用”过于绝对。可能仍扫描索引，部分系统有 skip scan，区别在于是否能有效缩小扫描范围。[PostgreSQL 多列索引](https://www.postgresql.org/docs/current/indexes-multicolumn.html)

确实需要按函数查，可考虑表达式索引，例如 PostgreSQL：

```sql
CREATE INDEX people_upper_surname_idx ON people (UPPER(surname));
```

表达式要满足产品对稳定性/不可变性的要求，查询表达式也要匹配；支持不代表优化器必选它。另一办法是维护派生列再索引，但要处理更新同步。不能只在 INSERT 时写一次，后来改姓却忘记派生值。

## 7. 自测

1. 只查 born，联合索引 `(surname,born)` 为什么不一定高效？答：缺第一层定位信息，可能扫描很大范围；不是绝对不能用。
2. 索引越多越好吗？答：要平衡查询收益、空间与写入成本。
3. 计划显示 Seq Scan，一定差吗？答：少量数据或高命中比例时可能合适。
4. 函数条件无法利用原列索引，怎么办？答：能改为原列范围就改，否则评估表达式索引、专用索引或一致维护的派生列。
