## 1. 登记一部电影为什么需要多步（p2–18）

用户输入电影、国家名、导演和演员，数据库却要保存国家代码、电影 ID、人物 ID 和身份联系。一次业务会跨表，且可能遇到国家不存在、人物找不到等错误。

解决：封装成存储过程，让调用方用 CALL 触发一个明确的业务入口，减少网络往返，并集中检查。函数通常用于返回计算结果，过程通常用于执行操作；过程也可有输出参数，不能只背成“过程绝对没有返回信息”。

课件登记过程的推理链：

1. 用 INSERT SELECT 从国家表取得代码并插入电影；检查是否插入一行。
2. 取得新电影 ID；补充建议 PostgreSQL 用 RETURNING movieid INTO 变量，比依赖 lastval 的隐含来源明确。
3. 把导演、两位演员参数用 UNION ALL 变成多行“人物及角色”。
4. 与 People 匹配，一次插入 Credits；对比应登记人数与实际影响行数，不足则抛异常。

为什么要 UNION ALL？同一人可既演又导，不能丢掉合法角色事实。为什么要检查影响行数？INSERT SELECT 没找到国家时可能只插入零行，不会自动给出你想要的业务错误。

参数中的空名在课件中用 `COALESCE(name,'*')` 匹配，隐含前提是星号不会成为真实姓名；补充 PostgreSQL 可用 IS NOT DISTINCT FROM 做 NULL 安全比较。姓名不天然唯一，生产设计宜传可靠人物 ID，并处理重复参数。

**过程本身不等于事务。** 电影与演职员要共同成功，仍需明确事务边界和异常行为；内部能否 COMMIT 取决于产品及调用上下文。课件固定两位演员是教学简化，不是推荐的通用参数设计。

## 2. 有人绕过过程直接写表，怎么办（p19–41）

触发器是指定数据库事件发生时自动执行的动作。它可规范化输入、检查难以声明的规则，或维护标题词索引等冗余数据。能用主键、外键、CHECK 表达的规则，优先声明约束；不要把所有设计问题藏进触发器。

选择触发器时分开回答：

| 问题 | 选择 |
| --- | --- |
| 哪种变化触发 | INSERT、UPDATE、DELETE 等，按产品支持 |
| 何时执行 | BEFORE、AFTER，另有产品特定 INSTEAD OF |
| 一条语句执行几次 | FOR EACH ROW 每行；FOR EACH STATEMENT 每语句 |
| 能看到哪些值 | INSERT 看 NEW，DELETE 看 OLD，UPDATE 两者都有 |

一条 INSERT SELECT 插入 100 行，行级触发器通常执行 100 次，语句级通常一次；零行语句也要考虑语句级触发器。修改即将写入的值可用 BEFORE ROW；记录成功变化常用 AFTER。AFTER 仍在事务内，**不代表已经 COMMIT**。

## 3. 怎样知道谁改了出生年（p42–54）

审计记录可以包括人物 ID、列名、旧值、新值、操作者和时间。UPDATE 要判断哪列真的变化；普通 `OLD.died <> NEW.died` 会漏掉 NULL 到已知值的变化。

以下为 PostgreSQL 独立演示，假定 People 存在：

```sql
CREATE TABLE people_died_audit (
  peopleid int, old_died numeric(4), new_died numeric(4),
  changed_by text, changed_at timestamptz
);
CREATE FUNCTION audit_died() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF OLD.died IS DISTINCT FROM NEW.died THEN
    INSERT INTO people_died_audit
    VALUES (NEW.peopleid, OLD.died, NEW.died, current_user, current_timestamp);
  END IF;
  RETURN NULL;
END;
$$;
CREATE TRIGGER people_died_trg
AFTER UPDATE ON people FOR EACH ROW EXECUTE FUNCTION audit_died();
```

IS DISTINCT FROM 把 NULL 的变化也纳入比较。这个例子只记录 died 的更新，完整审计还要另处理插入、删除及其他列。AFTER 行触发器的返回值被忽略；BEFORE 行触发器通常应按操作返回 NEW/OLD，RETURN NULL 可能跳过行操作。[官方触发器说明](https://www.postgresql.org/docs/current/plpgsql-trigger.html)

课件审计草稿中的 datetime、拼写和括号不要直接当 PostgreSQL 可执行代码；本例使用 timestamptz。普通写触发器无法审计 SELECT；审计表与原更新通常同事务回滚，不能当作独立保存失败尝试的日志。数据库身份也不自动等于应用登录用户。

## 4. 隐藏动作为什么增加排错难度（p55–67）

一条 UPDATE 可能连带写别表，再触发其他动作。要记录触发器依赖、递归风险、性能和权限，维护索引冗余还要照顾标题修改、删除，而不只是插入。

课件 p58 的“约束都在更新后检查”是简化，实际检查时点依约束与产品而异；行级触发器跨行检查还会遇到修改中状态和并发问题。不能仅靠“先查没有冲突”代替数据库唯一约束。

## 5. 自测

1. AFTER 审计写入以后主事务回滚，审计一定留下吗？答：普通同事务审计也回滚。
2. 一次改 20 行，行级触发器只执行一次吗？答：通常每行一次，要与语句级区分。
3. NULL 改为 1991，为什么 <> 不够？答：普通比较为 UNKNOWN，用 NULL 安全判断。
4. 调用过程能否自动保证所有步骤原子化？答：仍须正确事务和异常处理，不由封装名称保证。
