# 第 8 节：安全修改数据——更新、删除与函数

> 来源：CS213-DB-08.pdf，57 页；PDF 物理页码。更新：2026-11-16。
> [分节目录](README.md) · [大总结](../数据库原理复习总结.md)

## 1. 数据变了，应该循环一行行改吗（p2–10）

第 7 节讲新增和事务，这节继续问：已有信息怎样改变？UPDATE 是集合操作，一句可以影响零行、一行或很多行。没有 WHERE 会更新全表，影响零行也不等于报错。

课件用姓名中的 `von` 前缀说明批量转换：把满足模式的姓统一改为适合排序的形式。应先用相同 WHERE 做 SELECT，确认目标行和变换结果，再在事务中修改、检查影响行数，正确才提交。不要先查所有行，再让客户端逐条发 UPDATE；能用集合表达时通常能减少往返和重复工作。

更新一列也可能并不便宜。p10 衔接上一节：PostgreSQL heap 更新会产生行版本、维护必要索引并记录 WAL；HOT 可能减少索引维护，但还要求索引条件合适、同页有空间等，不能理解为“非索引列更新永远零成本”。

## 2. 用另一张表补资料，为什么更危险（p11–27）

情况：正式电影表缺片长和颜色，暂存表有。用片名匹配似乎可以，但同名重拍片会误配。因此应按当前业务键匹配国家、片名、年份，并保证每条目标记录最多匹配一个来源。

以下是扩展表 movies_2 和 us_movie_info 的 PostgreSQL 示例，假定已有 duration、color 等列，来源的 `(title,year_released)` 唯一：

```sql
UPDATE movies_2 AS m
SET duration = i.duration,
    color = CASE i.color WHEN 'C' THEN 'Y' WHEN 'B' THEN 'N' END
FROM us_movie_info AS i
WHERE m.country = 'us'
  AND m.title = i.title
  AND m.year_released = i.year_released;
```

先问三个问题：没有匹配会怎样？匹配一条是否正确？匹配多条会怎样？

- 标量子查询无行通常返回 NULL，可能把原值覆盖为空；只想改有来源的行，要加 EXISTS 等范围限制。
- 标量子查询多行在 PostgreSQL 中会报错；不能靠它自动挑正确版本。
- UPDATE FROM 多匹配不能保证选择哪条来源。课件“更新两次留下最后一次”的叙述不要当成通用执行规则，重点是结果不确定。[PostgreSQL UPDATE](https://www.postgresql.org/docs/current/sql-update.html)

典型反例：目标 King Kong(1976)，来源同时有 1933 和 1976；只连片名就无法决定片长该是 100 还是 134。

p26–27 主张标识符应稳定，这是设计建议。SQL 并不普遍禁止更新主键；能否更新取决于唯一性、外键引用与 ON UPDATE 等规则。不要为改变主键盲目删行重插，那可能丢失关联。

## 3. 已存在就改，不存在就插入（p28–31）

这是 upsert 需求。课件展示 MERGE、MySQL ON DUPLICATE KEY UPDATE、SQLite REPLACE。它们不能只按名称当作完全等价：REPLACE 可能先删除冲突行再新增，关联、触发器和 ID 都可能受影响。

补充推理：应用先查“没有”再插入，两个人可能同时查到没有。因此业务唯一约束仍需要存在；普通的“先 UPDATE，零行就 INSERT”也需要处理并发冲突，不能认为放进过程就自动安全。

## 4. 删除的目标也必须先讲清（p32–40）

DELETE 删除符合条件的行，不删除表结构；缺 WHERE 会清空记录。历史数据常先归档再删除活动记录，两个操作如果要求一起生效，就放同一事务。外键也会检查删除和更新，不只检查 INSERT。

TRUNCATE 面向整表清空，锁、触发器、外键、回滚与编号行为依产品而异。课件提醒它可能不可回滚，不能推广成所有系统都不可回滚：PostgreSQL 的 TRUNCATE 可随事务回滚。[官方说明](https://www.postgresql.org/docs/current/sql-truncate.html)

## 5. 复杂显示公式每次复制，怎样维护（p41–57）

前面把 `von Stroheim` 转成 `Stroheim (von)` 便于排序，显示姓名时又希望还原。课件先写长 CASE、SUBSTR、TRIM，再引出函数：把可复用的计算封装，传入参数、返回结果。

课件 p48 代码有拼接和字符笔误，理解其意图而不直接复制。一个简化、可运行的 PostgreSQL 示例：

```sql
CREATE FUNCTION display_name(fn text, sn text)
RETURNS text LANGUAGE sql AS $$
  SELECT CASE WHEN fn IS NULL THEN sn ELSE fn || ' ' || sn END
$$;
```

这里假定 sn 非空，仅演示封装，不负责还原所有姓名格式。函数参数与数据库列要避免重名歧义。过程语言还能写变量、条件、循环、游标和错误处理，但有循环能力不等于该把批量 SQL 改为逐行处理。

若函数每调用一次就查询国家名，外层上万行可能形成大量隐含查询。课件建议这种查表优先 JOIN，让优化器看见整体关系；这是性能取向，不是语法禁止函数查询数据库。SQLite 也属于 DBMS，只是用户定义函数常通过宿主程序注册，不能照抄课件“不是真 DBMS”的评价。

## 6. 自测与答案

1. 同名片有两个年份，只按标题更新为何危险？答：可能跨版本误配或出现多来源，不满足一目标一来源。
2. 子查询没匹配，是否总能保持原值？答：不能，可能用 NULL 覆盖，需要限制范围。
3. UPDATE 影响零行，程序可否当成业务成功？答：必须结合业务条件检查。
4. 函数与 JOIN 选哪个？答：纯表达式复用适合函数；跨表取标签优先把关系明确写成 JOIN，再看执行计划。
