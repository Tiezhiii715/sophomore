上一节解决了“表应该怎么拆”，这一节继续追问：**如果别人不按约定录数据，谁来拦？** 仅仅画好图、口头说“这个编号不能重复”，还不够，必须把规则写成数据库能执行的约束。

## 1. 先把“改盒子”和“改盒子里的东西”分清（p2–21）

课件介绍 SQL 的来历，是为了引出一种既能处理数据、也能描述结构的语言。

| 你想做的事 | 类别 | 典型语句 |
| --- | --- | --- |
| 新建表、加列、删掉整个表 | DDL，定义结构 | CREATE、ALTER、DROP |
| 新增、修改、删除记录 | DML，处理内容 | INSERT、UPDATE、DELETE |
| 查询符合条件的内容 | 查询；课程把它放在数据操作体系中 | SELECT |

`DELETE FROM movies` 是删记录，表还在；`DROP TABLE movies` 是把表对象本身删掉。日后事务中能否回滚 DDL，要按数据库和具体命令判断，第 7 节会继续讲。

第 1 节的关系模型要求元组不重复，SQL 却不会自动给任意建表语句加上这个保证。**语法能执行，不代表结构符合你想表达的规则。**

## 2. CREATE TABLE 能成功，为什么仍然可能是坏设计（p22–38）

```sql
CREATE TABLE people (
    peopleid INT,
    first_name VARCHAR(30),
    surname VARCHAR(30),
    born NUMERIC(4),
    died NUMERIC(4)
);
```

这段看起来挺完整，但它允许：编号缺失、姓名缺失、重复编号、死亡年早于出生年。系统只是知道“五列的类型”，还不知道“什么记录才算合法”。

所以建表不只是写列名，应该依次想：一行代表谁；每列什么类型；哪些必须填写；怎样唯一识别；引用的对象是否存在；哪些组合不合法。

### 2.1 类型决定这个格子能表达什么

| 数据用途 | 常见类型 | 需要想清楚的地方 |
| --- | --- | --- |
| 编号、整数计数 | INT | 范围是否够，不能存任意长数字 |
| 金额等精确小数 | NUMERIC/DECIMAL(p,s) | p 是总位数，s 是小数位数 |
| 近似测量结果 | FLOAT 等 | 二进制近似，不能假定所有小数都精确 |
| 固定长度代码 | CHAR(n) | 常见行为会补空格，注意比较规则 |
| 变长姓名、标题 | VARCHAR(n) | 长度与字符/字节细节依产品 |
| 日期、时刻 | DATE、TIMESTAMP 等 | 别把要做时间运算的数据只当显示文字 |
| 长文本、二进制 | TEXT/CLOB、BLOB/BYTEA 等 | 名称与限制依产品 |

`NUMERIC(6,2)` 的 6 是总位数，所以通常最多四位整数和两位小数。手机号和证件号即使全是数字，也未必适合数值类型：它们不是拿来加减的，前导 0 还可能有意义。

### 2.2 NULL 为什么需要单独考虑

课件 p33 引入 NULL：没有一个可用值，原因可能是未知、不适用、尚未录入。它不等于 0，也不等于空字符串。

`died` 可空，表示尚未登记死亡年；但仅凭 NULL，现实上未必能断言“确定健在”，那是示例业务的约定。`first_name` 也不该机械非空，有人只使用单名或艺名，课件因此把 surname 扩展理解为姓或艺名。

**NOT NULL 是业务决定，不是越多越好。** 真正不知道的信息若被迫随便填一个假值，数据反而更差。

## 3. 从“必须有值”到“必须是合法事实”（p39–56）

### 3.1 NOT NULL：该填的必须填

`peopleid INT NOT NULL` 禁止缺失，但两个人仍能填相同编号。它只管有没有，不管重复。

### 3.2 PRIMARY KEY：给一行一个可靠身份

主键要求唯一且非空。一张表一个主键，但这个主键可以由多列组成。

```sql
PRIMARY KEY (movieid, peopleid, credited_as)
```

这不是说每一列都分别唯一，而是三列组合唯一；允许同一 movieid 多次出现。

### 3.3 UNIQUE：挡住“换个编号再登记一次”

如果同一部电影被赋予两个 ID，主键不会报错。可在当前教学模型下增加：

```sql
UNIQUE (title, country, year_released)
```

候选规则必须符合业务。课件中人物姓名唯一也是教学假设，现实中不能仅凭同名断定同一人。UNIQUE 对 NULL 的处理还存在产品差异，因此它不能简单替代“非空候选键”的完整约束。

### 3.4 CHECK：检查一行内部的值和关系

```sql
CHECK (died IS NULL OR died >= born)
```

死亡年未知时允许录入；知道时不能早于出生年。只写 `CHECK (died >= born)`，遇到 NULL 常得到 UNKNOWN，而 CHECK 通常拒绝 FALSE、允许 UNKNOWN，所以它不能代替 NOT NULL。

课件 p48 说 MySQL 不执行 CHECK，这是旧行为。MySQL 8.0.16 起开始支持执行 CHECK，实际还应看约束是否声明为 NOT ENFORCED。[MySQL 官方文档](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html)

### 3.5 FOREIGN KEY：引用的对象先得存在

情况：电影国家代码录成 `ux`，只限制两位字符仍然会放行。把所有代码硬写到 CHECK 里，也不方便维护。

解决：国家表保存允许的代码，电影引用它。

```sql
FOREIGN KEY (country) REFERENCES countries(country_code)
```

外键还防止出现悬空引用：默认限制行为下，一个国家仍被电影引用，不能随便删除该国家。若配置级联等动作，行为会不同，不能一概说任何外键都会阻止父记录删除。

外键和主键不是互斥概念。Credits 中的 movieid 既是外键，也参与它自己的复合主键。外键也不强制每个父对象必须拥有子记录：国家存在但暂时没有电影完全可以。

## 4. 把前面的想法合成能执行的四张表

以下统一采用 PostgreSQL 兼容写法；country 使用小写代码，与后续例子一致。年份是数字年份，不是完整日期。

```sql
CREATE TABLE countries (
    country_code CHAR(2) PRIMARY KEY,
    country_name VARCHAR(80) NOT NULL UNIQUE,
    continent VARCHAR(30) NOT NULL
);

CREATE TABLE movies (
    movieid INT PRIMARY KEY,
    title VARCHAR(100) NOT NULL,
    country CHAR(2) NOT NULL REFERENCES countries(country_code),
    year_released NUMERIC(4) NOT NULL CHECK (year_released >= 1895),
    UNIQUE (title, country, year_released)
);

CREATE TABLE people (
    peopleid INT PRIMARY KEY,
    first_name VARCHAR(30),
    surname VARCHAR(30) NOT NULL,
    born NUMERIC(4) NOT NULL,
    died NUMERIC(4),
    CHECK (died IS NULL OR died >= born)
);

CREATE TABLE credits (
    movieid INT REFERENCES movies(movieid),
    peopleid INT REFERENCES people(peopleid),
    credited_as CHAR(1) CHECK (credited_as IN ('A', 'D')),
    PRIMARY KEY (movieid, peopleid, credited_as)
);
```

这个版本没有强制人物姓名唯一，避免将现实同名人物合并。若要逐项重现课件示范，需要另说明姓名唯一的模型假设。`credited_as` 当前只收 A/D，日后第 6 节加入 P 时，需要先调整 CHECK；约束也要随业务变化维护。

## 5. 规则写完了，如何把第一条数据放进去（p57–66）

情况：电影引用国家，所以先插国家，再插电影。演职员联系需要电影和人物已经存在。

```sql
INSERT INTO countries (country_code, country_name, continent)
VALUES ('it', 'Italy', 'EUROPE');

INSERT INTO movies (movieid, title, country, year_released)
VALUES (123, 'L''Avventura', 'it', 1960);
```

列名和值按位置一一对应。字符串用单引号；字符串内部的一个单引号写成两个，`L''Avventura` 实际只存一个撇号。

为什么明确列名？以后表增加一列，靠隐含列顺序的 INSERT 容易失败或错位。省略某列时，有默认值通常用默认值，否则通常为 NULL，再接受约束检查。课件这里只讲基本插入，第 7 节会展开默认值和自动编号。

日期也要消除歧义。补充 PostgreSQL 示例：`DATE '1969-07-20'`；Oracle 课件演示 `TO_DATE(..., 格式)`。不要依赖 `'11/05/2026'` 自动猜到底是 11 月 5 日还是 5 月 11 日。`CURRENT_DATE`、`CURRENT_TIMESTAMP` 等当前时间表达式的支持和细节依产品核对。

## 6. SQL 能成功，不等于所有事实都正确

约束能挡住违反已声明规则的数据，却不知道某人的出生年是否查错，也不会替你识别所有拼错的电影名。应用仍需检查业务输入和数据库返回结果。

另外，关键字大小写、对象名大小写、字符串比较是三个问题：SQL 关键字通常不分大小写；引号标识符、文件系统和 collation 会影响其他行为，不能简单背成“SQL 一律不分大小写”。

## 7. 自测

1. 外键引用国家表，是否意味着每个国家至少有一部电影？<br>
   答：不意味着。外键检查子行的引用，不要求父行必须被引用。
2. `UNIQUE(movieid, peopleid)` 与两列分别 UNIQUE 一样吗？<br>
   答：不一样，前者只要求组合唯一。
3. 出生年填成 1800，但所有约束都通过，能说明真实正确吗？<br>
   答：只能说明没违反已声明规则，不能证明现实事实准确。
4. CHECK 已限制范围，为什么还会需要 NOT NULL？<br>
   答：NULL 比较可能得到 UNKNOWN，不能指望范围 CHECK 自动拒绝缺失。

这节学完，你应该能把一条中文业务要求翻译成类型、非空、唯一、检查或外键规则，并解释每种约束分别挡住了什么错误。
