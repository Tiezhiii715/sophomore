这一节每一部分都围绕“结果怎么会少了或多了”：内连接让缺资料的电影消失，错误去重把两年的事实合成一年，子查询改写成 JOIN 后可能凭空多出重复。

## 1. 明明有这部电影，查导演时为什么没了（p2–9）

上节用 Movies → Credits → People 查导演。若某部片已经录入，但导演联系尚未录入，内连接找不到匹配，它就消失。

先分清需求：

- “资料完整、已知导演的电影”可以只保留匹配。
- “所有电影，导演有就显示”必须保留没有匹配的电影。

第二种情况用 LEFT JOIN：找得到右边就配上，找不到仍留左边记录，右边各列补 NULL。左表选你要完整保留的对象。

这里的完整保留仍然受后续 WHERE 等条件影响，所以“用了 LEFT JOIN，左表绝不会少”并不成立。

## 2. 第一个难点：保留补空行之后，别亲手再删掉它（p10–29）

### 2.1 两张右表连续连接，要照顾整条链

```sql
FROM movies m
LEFT JOIN credits c ON c.movieid = m.movieid
JOIN people p ON p.peopleid = c.peopleid
```

电影没 Credits 时，c.peopleid 是补出的 NULL，后面的内连接又匹配失败，电影还是丢了。沿着这条可选联系继续取 People 时，也需要 LEFT JOIN。

### 2.2 两次 LEFT JOIN 后，为什么 WHERE 仍有问题

如果写 `WHERE c.credited_as = 'D'`，补空行的这个比较为 UNKNOWN，照样被过滤。有人试着补 `OR c.credited_as IS NULL`，课件用一个很有价值的反例拆穿它：

```text
电影 A：只有演员联系，没有导演联系
```

第一次连接能匹配演员，所以不会产生“没有匹配才补的 NULL 行”。连接结果 c.credited_as 是 A，既不是 D 也不是 NULL，于是电影仍被删。

**原因：你先匹配了“所有演职员”，再筛导演；你真正需要的是先只找导演，找不到导演也保留电影。**

### 2.3 正确地把“什么才算匹配”写进 ON

```sql
SELECT m.movieid, m.title, p.peopleid, p.first_name, p.surname
FROM movies m
LEFT JOIN credits c
       ON c.movieid = m.movieid AND c.credited_as = 'D'
LEFT JOIN people p ON p.peopleid = c.peopleid
WHERE m.country = 'gb';
```

这样即使 A 只有演员，仍算“没找到导演匹配”，返回一条导演信息为 NULL 的电影记录。课件也用“先子查询筛出导演，再左连接”的方式表达同样逻辑。

自己验算四种数据：没任何演职员、只有演员、一个导演、两个导演。正确结果分别是保留一行补空、保留一行补空、一行导演、两行导演。

## 3. 没电影的国家，怎样统计成 0（p11–18）

直接对 Movies 分组，没有电影的国家根本不会形成分组。解决有两条路线。

第一条：先统计有电影的国家，再让完整国家表 LEFT JOIN 统计结果，缺失值用 COALESCE 显示为 0。

```sql
SELECT c.country_code, c.country_name, COALESCE(x.cnt, 0) AS movie_count
FROM countries c
LEFT JOIN (
    SELECT country, COUNT(*) AS cnt
    FROM movies
    GROUP BY country
) x ON x.country = c.country_code;
```

第二条：先左连接电影，再数匹配到的电影 ID：

```sql
SELECT c.country_code, c.country_name, COUNT(m.movieid) AS movie_count
FROM countries c
LEFT JOIN movies m ON m.country = c.country_code
GROUP BY c.country_code, c.country_name;
```

为什么第二条不能随便 COUNT(*)？零电影国家仍有一条补空记录，COUNT(*) 会数成 1；电影主键 m.movieid 在真实匹配行必非空，COUNT(m.movieid) 才会得到 0。

COALESCE 返回第一个非 NULL 参数。只在“没有匹配就明确代表零部电影”的语境下用 0 替代，未知金额、未知年龄不能不问含义就全变 0。

课件着重讲 LEFT JOIN，RIGHT JOIN 可以交换两边改写，FULL JOIN 则用于两边都保留。理解保留语义即可，不必把课件的使用偏好当成 FULL JOIN 没有用途。

## 4. 两份结果上下拼，为什么 UNION 会少算（p30–52）

JOIN 是按条件横向配对，UNION 是把兼容的结果纵向合并。纵向合并要求列数相同，对应位置类型兼容；它按位置配列，不按别名自动找同名字段。

| 运算 | 作用 |
| --- | --- |
| UNION | 两批结果合并，再对整行去重 |
| UNION ALL | 保留两批结果全部行，包括重复外观 |
| INTERSECT | 默认集合语义下保留共同的不同整行 |
| EXCEPT | 默认集合语义下保留左侧有、右侧没有的不同整行 |

部分产品/版本支持 ALL 变体；Oracle 课件使用 MINUS 表示差集，具体支持按版本核对。

### 4.1 两条看起来相同的行，可能是两件真实事实

去年电影 1 看了 100 次，今年也看了 100 次：

```text
去年结果：(1,100)
今年结果：(1,100)
```

UNION 只留一条，再 SUM 得到 100，正确应为 200。因此要用 UNION ALL：

```sql
-- 假定这两张扩展表已存在，每行记录一次或一批观看量
SELECT movieid, SUM(view_count) AS total_views
FROM (
    SELECT movieid, view_count FROM last_year_data
    UNION ALL
    SELECT movieid, view_count FROM current_year_data
) x
GROUP BY movieid;
```

课件还增加 period 列说明两行来自不同时期。**是否去重由事实身份决定，不能因为数值恰好相等就删掉。** UNION ALL 不只是“确信不会重复才允许用”，它也适用于重复外观本来就应该保留的情况。

### 4.2 差集也可以用“找不到匹配”表达

找没有电影的国家：先保留所有国家，再检查电影主键补空：

```sql
SELECT c.country_code, c.country_name
FROM countries c
LEFT JOIN movies m ON m.country = c.country_code
WHERE m.movieid IS NULL;
```

必须检查真实记录中非空的右表列。若检查一个原本就可空的属性，就无法区分“没有匹配”与“匹配到了，但属性未知”。

## 5. 子查询只是把一个问题先算出来，再用于另一个问题（p53–71）

### 5.1 放在 FROM：把结果当临时表

前面的国家电影数就是例子。一行一个国家，外层继续连接它。需要明确列名和别名，方便外层引用。

### 5.2 放在 SELECT：为当前行求一个值

```sql
SELECT m.movieid, m.title,
       (SELECT c.country_name
        FROM countries c
        WHERE c.country_code = m.country) AS country_name
FROM movies m;
```

内层使用外层 m.country，因此是相关子查询。它作为一个标量位置，必须最多返回一行一列：0 行通常变成 NULL，1 行取该值，多行报错。这和 LEFT JOIN 在右边不唯一时展开多行不同。这里 country_code 是主键，保证最多一行。

课件用“每行触发一次”帮助理解相关性，实际执行可能被优化器改写，不能据此断言物理上一定重复执行多少次。

### 5.3 放在 WHERE：回答属于哪些值

```sql
SELECT movieid, title
FROM movies
WHERE country IN (
    SELECT country_code FROM countries WHERE continent = 'EUROPE'
);
```

内层生成欧洲代码，外层判断成员资格。IN 不会因为内层同一个值出现两次，就把外层记录复制两遍。

如果改写为 JOIN，右边同一匹配值有多行，就会放大外层。这里 Countries 的主键保证安全；换成其他中间结果时要重新检查唯一性，不能机械替换。

补充：课件说 FROM 子查询不能相关，通常指普通派生表；PostgreSQL 的 LATERAL 可显式访问前面的 FROM 项。[官方表表达式文档](https://www.postgresql.org/docs/current/queries-table-expressions.html#QUERIES-LATERAL)

## 6. 最容易漏掉的反例：NOT IN 遇到 NULL（p72–79）

问题：找“不在名单 a、b 里”的值。正常情况 `x NOT IN ('a','b')` 相当于同时不等于 a 和 b。

如果名单有 NULL：

```text
'c' NOT IN ('a','b',NULL)
= TRUE AND TRUE AND UNKNOWN
= UNKNOWN
```

WHERE 不保留 UNKNOWN，因此 c 也不见了。如果 x='a'，结果是 FALSE，不是 UNKNOWN，但同样不会保留。所以准确说法是：名单含 NULL 时，没有匹配的值也可能无法被判为 TRUE，不能粗略说所有情况都为 NULL。

可从内层排除 NULL，但外层自己的 NULL 仍要按题意处理。若要表达“一个相关记录也没有”，通常 NOT EXISTS 更直接。

## 7. 问“有没有”，就不必把所有匹配都展开（p80–88）

“至少有一位 1970 年以后出生演员的电影”：

```sql
SELECT m.movieid, m.title
FROM movies m
WHERE EXISTS (
    SELECT 1
    FROM credits c
    JOIN people p ON p.peopleid = c.peopleid
    WHERE c.movieid = m.movieid
      AND c.credited_as = 'A'
      AND p.born >= 1970
);
```

内层引用当前电影 ID，是在问“能找到这样的演员行吗”。有一个就足够，不需要为每位演员输出一部电影。`SELECT 1`、`SELECT NULL` 在这个普通存在性查询中都不影响是否存在行。

“没有任何演员记录的电影”：

```sql
SELECT m.movieid, m.title
FROM movies m
WHERE NOT EXISTS (
    SELECT 1 FROM credits c
    WHERE c.movieid = m.movieid AND c.credited_as = 'A'
);
```

要保证相关条件没忘：若漏掉 `c.movieid = m.movieid`，内层问的就变成“全库有没有演员”，不再针对每部电影。

课件建议相关场景使用 EXISTS，但相关 IN 并非语法禁令。性能也不能仅凭“相关一定慢”判断。[PostgreSQL 子查询文档](https://www.postgresql.org/docs/current/functions-subquery.html)

## 8. 自测

1. 只有演员没有导演，`WHERE role='D' OR role IS NULL` 为什么救不回来？<br>
   答：已匹配到演员，不会补空，随后演员行被过滤。
2. 两年的观看数恰好相等，为什么仍要两行？<br>
   答：它们代表不同时期的事实，应先保留再求和。
3. IN 改 JOIN 时，先检查什么？<br>
   答：右边每个匹配值是否唯一，否则外层会被复制。
4. EXISTS 内层 SELECT NULL 会表示“不存在”吗？<br>
   答：不会，存在性看是否返回行，不看这个普通查询投影的常数。

写完后至少构造一个“只有部分关联资料”的对象和一个含 NULL 的样本。能正确处理它们，才算抓住了本节。
