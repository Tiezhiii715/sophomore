这一节看起来讲了四件事，实际都在回答同一个问题：**把课堂上的 SQL 放进一个真实的多人系统，还会发生什么？** 用户会拼错字、一次操作可能改好几张表、两个人可能同时插入、数据还可能来自一个格式不整齐的文件。

## 1. 用户记得的是意思，数据库存的是字：怎样把电影找出来（p2–20）

### 1.1 等号遇到现实输入，就开始漏结果

假设数据库保存 `2001: A Space Odyssey`，用户输入 `2001, a space odyssey`。人知道它们指同一部片，直接比较字符串却可能因为标点、大小写不同而失败。课件继续用 Gielgud 姓氏的错拼、周姓的不同转写，以及成龙的简繁体和英文名，说明问题不止是大小写。

先区别几种需求：

| 用户手里的线索 | 比较对象 | 合适的思路 |
| --- | --- | --- |
| 准确 ID | 值是否相等 | `movieid = 42` |
| 记错几个字母 | 字符是否相近 | 拼写相似度、别名或常见错拼映射 |
| 记得标题里的词 | 词是否出现 | 全文搜索 |
| 只记得剧情意思 | 描述含义是否接近 | 向量语义搜索 |

**这些需求不能靠同一种索引和一个等号全部解决。** 大小写归一化只能解决大小写，无法自动知道 `Matrix 2` 和某个地区译名是一部片。别名、翻译映射和搜索模型各有作用。

### 1.2 标点不可靠，那就先拆成词

问题：完整标题稍有不同就匹配失败。

解决：把标题拆词，统一格式，去掉过于常见、区分度很低的词，再记录“这个词出现在哪部电影里”。例如得到：

```text
2001    → 电影 42
SPACE   → 电影 42、电影 65
ODYSSEY → 电影 42、电影 77
```

这就是课件用普通表演示的倒排思路：**由词找电影，而不是每次由电影全文找词。**

```sql
CREATE TABLE movie_title_ft_index (
    title_word VARCHAR(30) NOT NULL,
    movieid INT NOT NULL REFERENCES movies(movieid),
    PRIMARY KEY (title_word, movieid)
);
```

复合主键的含义：同一部片里的同一个词，只记一次。不同电影当然可以共享同一个词。查询输入也要走相同的拆词和标准化过程，否则存的时候用 `SPACE`，查的时候用另一套规则，还是可能找不到。

课件提到真正的全文引擎还会做词干化等语言处理。补充：具体是否做、怎么做取决于语言和配置；中文的分词方式也不能照搬英文空格拆词。

### 1.3 找到很多候选片，怎样判断哪个更像

问题：`SPACE` 可能出现在很多片名里，只匹配一个词不够。

解决：先按电影统计命中的不同查询词数量，再按命中数排名。此处利用了第 4 节的分组和第 6 节的窗口排名。

```sql
WITH hits AS (
    SELECT movieid, COUNT(*) AS hit_count
    FROM movie_title_ft_index
    WHERE title_word IN ('2001', 'SPACE', 'ODYSSEY')
    GROUP BY movieid
), ranked AS (
    SELECT movieid, hit_count,
           RANK() OVER (ORDER BY hit_count DESC) AS rnk
    FROM hits
)
SELECT m.movieid, m.title, r.hit_count
FROM ranked r
JOIN movies m ON m.movieid = r.movieid
WHERE r.rnk = 1;
```

假设电影 42 命中三个词，65 和 77 各命中一个，42 排第一。若两部都命中三个，`RANK() = 1` 会保留两部。课件特意保留并列，因为数据库没有足够证据替用户做唯一决定。

为什么这里 `COUNT(*)` 可以数命中词？因为 `(title_word, movieid)` 唯一。若把索引表改成一词重复多行的结构，同一查询就可能高估命中数。这又回到了“一行是什么”。

问题还没完全解决：搜索 `Casablanca`，标题恰好是这个词的片子，与包含它的更长标题都可能命中一次。课件提出比较除去查询词后的剩余长度、展示多个候选等策略。它们是启发式规则，不能保证每次猜中用户意图。错拼也可以建立常见变体映射，但词命中本身不会自动纠正任意错字。

### 1.4 连标题都想不起来，就比较描述的含义

用户说：“人们生活在一个模拟世界里的电影。” 这句话可能没有片名里的任何词。

解决：提前把电影描述编码成向量，搜索时用同一套兼容的模型编码用户输入，再比较向量距离。向量可以先理解成“模型给一段话安排的一串坐标”。意思相近的文字希望在这个坐标空间里更近，但模型也可能理解错。

课件 p18 的 PostgreSQL + pgvector 示例：

```sql
-- 前提：安装 pgvector，movie_search.embedding 为匹配维度的 vector 列。
-- $1 是程序绑定的查询向量参数，不是直接复制到普通控制台的字面值。
SELECT movieid, title,
       embedding <=> $1::vector AS distance
FROM movie_search
ORDER BY embedding <=> $1::vector
LIMIT 5;
```

`<=>` 在 pgvector 中表示余弦距离，此处越小越靠前。全文搜索比较词，语义搜索比较向量；语义搜索并不承诺识别出“唯一正确电影”。课件同时提到 openGauss DataVec，语法应按实际产品核对。

### 1.5 数据多了，逐个算距离太慢

问题：要找最近的 5 个，每个向量都算一遍，数据大时工作量很高。

解决：HNSW 用多层图寻找附近候选，通常可以减少搜索工作，但它属于近似搜索，可能漏掉真正的最近邻。

```sql
-- PostgreSQL + pgvector
CREATE INDEX movie_embedding_hnsw
ON movie_search USING hnsw (embedding vector_cosine_ops);
```

不能只测“快不快”，还要测“漏多少”。例如精确前 5 个是 A、B、C、D、E，近似返回 A、B、C、F、G，则这个例子的 recall@5 是 3/5。它衡量找回精确邻居的比例，不等于用户满意度。

加入 `WHERE country = 'cn'` 之类的过滤后还要重新测。近似候选可能很多不满足条件，结果数量和召回率都会受影响。[pgvector 官方说明](https://github.com/pgvector/pgvector#filtering)也特别讨论了过滤。

### 1.6 关键词和语义各有所长，怎样合并

问题：两条搜索路线的分数不是一个量纲，不能随便相加。

解决：课件介绍 RRF，使用各自的名次融合：

```text
RRF(movie) = 1 / (c + 关键词名次) + 1 / (c + 向量名次)
```

`c` 是预先选定的平滑常数，某路没出现就贡献 0。用教学取值 `c=60`：电影 42 的两路名次是 1、3，得分约 0.03227；电影 65 是 4、1，约 0.03202；只在向量第 2 名出现的电影 77 得约 0.01613。常数取值是例子，不是课件要求固定使用 60。

**合并依据是 `movieid`。** `(42, 1)` 和 `(42, 3)` 是不同整行，`UNION` 不会因为电影相同就自动把名次融合。应把两路按 ID 对齐，或者 `UNION ALL` 保留两路贡献后 `GROUP BY movieid` 求和。每一路先保证一部片只有一个名次。

## 2. 一次操作改两处，怎样保证不会只完成一半（p21–44）

### 2.1 转账为什么不能只看两句 UPDATE

你有 300 元，另一个账户有 1600 元，要转 100 元。扣款成功后变成 200，如果数据库在加款前崩溃，总金额就少了 100。

解决：把两个修改放在同一个事务里。它们共同构成一个业务单位，要么一起完成，要么都不保留。

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

这段用于解释事务边界，假定 `accounts(id,balance)` 和两条账户记录已经存在。真实程序还必须检查余额、收款账户是否存在、影响行数等。**UPDATE 影响 0 行不一定报错**：收款账户不存在时，不能因为 SQL 都“执行成功”就提交。

应用逻辑应是：开启事务；执行并检查每一步；全部满足业务条件才 `COMMIT`；任何一步不满足都 `ROLLBACK`。不能把 `ROLLBACK` 写在 `COMMIT` 后面当撤销按钮。提交以后需要新的业务补偿，不能靠回滚原事务恢复。

### 2.2 ACID 分别解决哪种担心

| 属性 | 最通俗的担心 | 对应意思 |
| --- | --- | --- |
| A 原子性 | 扣了钱却没加上 | 多个修改作为一个整体完成或取消 |
| C 一致性 | 操作后违反了规则 | 正确的事务和约束应保持业务规则成立 |
| I 隔离性 | 别人会看到半成品吗 | 按隔离级别控制并发可见性和相互影响 |
| D 持久性 | 成功后重启就没了 | 在相应持久化配置下，已提交结果能经受崩溃 |

一致性不能理解成“数据库自动懂所有业务”。它不知道你少给另一个账户加钱了，除非约束或应用逻辑把相应规则落实了。隔离也不意味着所有事务总是逐个串行执行。

### 2.3 为什么普通查询不一定等别人写完：MVCC

问题：别人正在改余额，我是等他结束，还是读取他还没确认的新数？

课件用 PostgreSQL heap 演示 MVCC：旧版本余额 8000，事务 900102 写出新版本 7500。旧行和新行暂时并存，系统依据事务状态和快照判断哪个版本对当前查询可见。

可以把快照理解成“本次阅读允许看到哪些已经确认的事实”。其他会话的普通读在修改提交前通常还能读旧版本。写入仍可能持有锁，冲突写入会等待；MVCC 不是“数据库不需要锁”。本事务通常也能读到自己已经做的修改。

p41 的 `xmin/xmax` 表用于说明创建和更新版本的事务标记。补充：真实 `xmax` 还可能涉及锁等状态，不能只看一个号码就独立判断可见性。

### 2.4 对方提交以后，我马上能看见吗

沿着课件 p42 的时间线：

| 时刻 | 会话 A | 会话 B |
| --- | --- | --- |
| 1 | 开事务，把 8000 改为 7500，尚未提交 | |
| 2 | | 开事务，第一次查询读到 8000 |
| 3 | 提交 | |
| 4 | | 再查询一次 |

在 PostgreSQL 中，B 使用 `READ COMMITTED`，两次普通查询分别取得语句快照，所以第二次能看到 7500；B 使用 `REPEATABLE READ`，沿用事务的固定快照，第二次仍看到 8000。

更精确地说，PostgreSQL 的可重复读快照由事务中第一条非事务控制语句建立，不能简单记作执行 `BEGIN` 那一瞬间拍照。这里讨论的是 B 读取 A 的修改，不否认 B 能读自己的修改。可重复读也不自动等于可串行化。[官方隔离级别文档](https://www.postgresql.org/docs/current/transaction-iso.html)

### 2.5 COMMIT 到底在等什么：WAL

问题：改动先在内存缓冲区里，断电后怎么办？难道每次提交都要立刻把全部数据页写到磁盘？

解决：先记可用于恢复的日志。WAL 的关键顺序是：**对应日志必须先持久化，相关数据页才可以落盘。** 在课件讨论的同步提交条件下，提交等待必要 WAL 持久化，数据页可以稍后再写。崩溃后，系统可利用日志恢复。

别记成“COMMIT 把所有表都刷一遍”。也别记成“有 WAL 就不会丢”，持久性还依赖提交和存储配置。这里没有展开日志格式、检查点和完整恢复算法。[PostgreSQL WAL 文档](https://www.postgresql.org/docs/current/wal-intro.html)

### 2.6 回滚是否等于拿旧备份覆盖整个数据库

不是。只取消本事务未提交的修改，其他事务已提交的内容保留。

课件 p44 对比：PostgreSQL heap、openGauss Astore 可利用事务可见性让已取消版本不再作为有效数据可见；openGauss Ustore 的历史保存在 Undo 空间，通过 Undo 动作处理回滚。理解时抓住“取消自己的修改”即可，具体实现依赖存储引擎；不可推广成所有系统一律把整页物理改回原样。

### 2.7 应用里还有哪些容易误会的地方

- **自动提交**：有些工具或驱动默认每条语句单独提交。两句 UPDATE 看着写在一起，也可能属于两个事务。先确认实际事务边界。
- **DDL 差异**：课件比较 MySQL/Oracle 的隐式提交与 PostgreSQL 可事务化的许多 DDL。不能把它背成所有 DDL 都一样，具体命令有例外。[MySQL 隐式提交清单](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)
- **转账流水**：只改余额缺少可追溯事实。可同一事务写流水并更新余额，也可从流水计算余额，取决于设计，课件没有规定只能选其中一种。
- **点赞**：只加计数挡不住重复点赞。用 `(videoid, memberid)` 作为唯一键记录“谁给什么点过赞”；若还维护缓存计数，需要保持它与明细一致。IP 不能可靠代表唯一用户。
- **删除**：历史订单还引用商品时，常见做法是更新状态让它下架，保留历史引用。软删除后，查询必须知道是否筛掉不活跃记录；软删除不是所有删除需求的唯一答案。

## 3. 多个人一起新增，ID 谁来分配（p45–62）

### 3.1 INSERT 先把列和值对应清楚

```sql
INSERT INTO movies (movieid, title, country, year_released)
VALUES (101, 'Example A', 'cn', 2024),
       (102, 'Example B', 'cn', 2025);
```

例子假定 `cn` 已存在且 ID 与业务唯一键未冲突。显式写列名，避免以后增加列时依赖隐含顺序。

省略某列时：有默认值就采用默认值，没有默认值通常得到 NULL，再由约束判断是否允许。**显式写 NULL 通常不会触发默认值。** 不要把“有默认值”误认为“任何空值都会自动替换”。课件 p46 称 SQLite 不支持多行 VALUES，这一说法过时，当前 [SQLite 官方 INSERT 文档](https://www.sqlite.org/lang_insert.html)明确支持。不同 Oracle 版本也需要分别核对，不能照抄旧结论。

### 3.2 MAX(id)+1 看上去合理，为什么会撞号

```text
当前最大 ID = 100
A 查询最大值 → 得 100 → 打算用 101
B 查询最大值 → 得 100 → 也打算用 101
A 插入 101 成功
B 插入 101 触发主键冲突
```

主键成功保护了数据库，但应用还是失败了。即使外面包了普通事务，也不能自动让“读最大值再插入”变成安全的号码分配器。

解决：使用数据库提供的序列或自动编号列，让系统处理并发分配。

### 3.3 序列：取新号与找回刚取的号

PostgreSQL 示例：

```sql
CREATE SEQUENCE movie_seq; -- 教学例子假设是新序列，与既有 ID 不冲突
SELECT nextval('movie_seq'); -- 为本次调用分配新号
SELECT currval('movie_seq'); -- 本会话对该序列最近取得的号
```

`currval` 不是“全库最后一个人的号”。它针对本会话和指定序列；本会话尚未调用过 `nextval` 时，`currval` 会报错。给已有数据的表接序列时，必须正确设置起点，不能从 1 开始就假定不冲突。手工插入 ID、重置序列等操作也可能造成冲突，主键约束仍有必要。

补充：PostgreSQL 的 `nextval` 分配通常不会因为事务回滚而收回，所以序号有空洞很正常。**唯一标识、连续编号、提交先后顺序是三种不同要求。** [官方序列函数文档](https://www.postgresql.org/docs/current/functions-sequence.html)

### 3.4 自动编号列：插入时让数据库替你取号

课件展示 PostgreSQL `serial`、MySQL `AUTO_INCREMENT` 等。补充一个 PostgreSQL identity 写法：

```sql
CREATE TABLE demo_movies (
    movieid INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title VARCHAR(100) NOT NULL
);
INSERT INTO demo_movies (title)
VALUES ('A New Film')
RETURNING movieid;
```

这是独立演示表，不要求改动前 6 节统一模型。`RETURNING` 是 PostgreSQL 写法，直接取回本条插入结果，方便把 ID 传给后续子表插入。[官方 RETURNING 文档](https://www.postgresql.org/docs/current/dml-returning.html)

课件还展示 `lastval()`、`last_insert_id()`。注意取值范围和产品差异：PostgreSQL `lastval()` 是本会话最近使用的序列，不限定某张表；触发器若使用别的序列，就可能让“最后一个号”不再是你想要的电影号。能直接返回本次插入 ID 时，优先把返回值明确传递给后续操作。自动生成 ID 也不替代标题等业务唯一规则。

## 4. 一万条文件记录，怎样变成几张干净的表（p63–83）

### 4.1 表单一次一条，文件需要批量处理

问题：逐行手工 INSERT 太繁琐，而且外部文件结构经常不符合规范化设计。

课件给出的路线是：**文件先进入暂存表（staging table），核对、清洗后，再用 `INSERT ... SELECT` 分发到正式表。** 暂存表可以接近原文件结构，正式表仍按实体和联系设计。

```sql
-- 教学暂存结构，假定这些字段都已能解析成相应类型
CREATE TABLE us_movie_info (
    title VARCHAR(100) NOT NULL,
    year_released NUMERIC(4) NOT NULL,
    duration INT NOT NULL,
    color CHAR(1) NOT NULL,
    PRIMARY KEY (title, year_released)
);
```

暂存不意味着完全不检查，课件这张暂存表仍有类型、非空和主键约束。补充：如果原始数据脏得连年份都可能是“未知”，可以先用宽松的文本暂存表并保存错误行，清洗后再转类型；这是更宽松的导入策略，不是说课件已经要求这样建表。

课件 p71 称 MySQL 不接受 NUMERIC、必须用 DECIMAL，这一说法需要校正：MySQL 中 NUMERIC 是 DECIMAL 的同义类型。[MySQL 官方定点类型文档](https://dev.mysql.com/doc/refman/8.4/en/fixed-point-types.html)

### 4.2 第一件事不是写 SQL，而是看文件

要确认：编码、列顺序、分隔符、引号、是否有表头、空串与 NULL 的表示、换行规则。Linux 常见 LF，Windows 常见 CRLF，但应检查实际文件，不能只凭文件来自哪台电脑判断。

```csv
"Title, With Comma",2024,120,C
"He said ""Hello""",2025,95,B
```

第一行标题本身含逗号，第二行标题含双引号。简单按逗号 `split` 会把第一行拆坏；CSV 要交给理解引号规则的解析器。制表符文件也要知道真正的分隔符是 Tab，不能随便当成若干空格。

### 4.3 文件在谁的机器上，决定谁去读

| 系统/工具 | 文件在服务器 | 文件在客户端 |
| --- | --- | --- |
| PostgreSQL | SQL `COPY ... FROM` | psql 命令 `\copy ... FROM` |
| MySQL | `LOAD DATA INFILE` | `LOAD DATA LOCAL INFILE`，受服务和客户端配置约束 |
| Oracle | 外部表、已授权目录等 | SQL*Loader 等工具，需控制文件描述映射 |
| SQLite CLI | 同一进程可访问的本地路径 | `.import`，无需网络数据库服务器 |

课件中 `/tmp/...` 不是“永远代表你电脑上的临时文件”。对服务器端 COPY，它是服务器上的路径；对 psql 的 `\copy`，路径由运行 psql 的客户端解释。

```sql
-- PostgreSQL：服务器文件；假定文件含表头，实际无表头时去掉 HEADER
COPY us_movie_info (title, year_released, duration, color)
FROM '/tmp/us_movie_info.csv'
WITH (FORMAT csv, HEADER true);
```

```text
-- psql 客户端命令，不是发给服务端的一般 SQL。这里也假定有表头。
\copy us_movie_info (title, year_released, duration, color) FROM 'E:/data/us_movie_info.csv' WITH (FORMAT csv, HEADER true)
```

`\copy` 示例写成一行便于直接在 psql 输入。权限、路径和数据格式都正确才会成功。[COPY 官方文档](https://www.postgresql.org/docs/current/sql-copy.html) · [psql 官方文档](https://www.postgresql.org/docs/current/app-psql.html#APP-PSQL-META-COMMAND-COPY)

### 4.4 导进暂存表不等于任务完成

接着检查重复业务键、缺失国家代码、非法年份、字段转换失败，再写进目标表。假定正式 `movies` 已配置自动 ID，且本批已清洗、去重、国家代码存在：

```sql
INSERT INTO movies (title, country, year_released)
SELECT s.title, 'us', s.year_released
FROM us_movie_info s;
```

第 2 节的原始 `movies` 若仍要求手工 ID，这段不能直接运行，必须先提供 ID 或配置生成方式。重复导入同一文件时也要决定如何处理已存在的业务记录，不能用新 ID 把同一事实再存一次。

课件最后提到 XML、JSON，以及用脚本应对奇怪格式。补充实践：脚本优先用参数化语句或可靠导入接口；不要把文件内容未经处理直接拼进 SQL。导入后核对有效行数和拒绝行数，再提交需要作为一个整体生效的修改。

## 5. 盖住答案，检查自己是否理解

1. 两部片的关键词分数都第一，为什么不直接 `ROW_NUMBER() = 1`？<br>
   答：那会强行只留一部；没有足够判据时应保留并列或让用户选择。
2. HNSW 返回得快，就算搜索成功了吗？<br>
   答：还要比较精确搜索结果、召回率和实际相关性，加入过滤后重新测。
3. 收款账户不存在，第二条 UPDATE 影响 0 行，事务一定自动失败吗？<br>
   答：不一定，应用必须检查影响行数，条件不满足就回滚。
4. A 提交后，B 再读一定看到新余额吗？<br>
   答：取决于隔离级别和快照；课件的 PostgreSQL 可重复读示例仍看到旧余额。
5. 序列用了 101，插入又回滚，下次一定还是 101 吗？<br>
   答：PostgreSQL 不保证收回，号码有空洞正常。
6. 文件明明在自己电脑上，服务端 COPY 为什么找不到？<br>
   答：服务端解析的是服务器路径。用客户端工具相应的本地导入命令。

本节的理解目标：你能把一次“搜索后新增电影和演职员”的操作拆开，说明搜索如何挑候选、事务怎样保证修改成组、ID 如何安全取得、批量数据又该如何先检查再进入正式模型。
